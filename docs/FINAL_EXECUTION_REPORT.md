## 📚 手动解决冲突方法论

### 我实际采用的方法

**Step 1：分析冲突**
```bash
# 查看补丁想要做什么
grep -B 5 -A 10 "conflicting_function" /tmp/patch-5.4.XXX

# 查看小米代码
sed -n 'start,end p' file.c
```

**Step 2：决策**
- 安全补丁 → 必须应用
- Bug修复 → 应该应用
- Vendor代码 → 谨慎修改
- API变化 → 评估影响

**Step 3：手动修改**
```bash
vim file.c
# 手动应用改动，保留关键代码
```

**Step 4：验证**
```bash
make file.o  # 编译测试
```

**Step 5：记录**
```bash
git commit -m "fix: manually resolve conflict in file.c"
```

### 实际执行示例

**案例：stmmac_main.c冲突**

```diff
补丁想要修改：
```

## 🎓 经验教训

### 1. 增量更新的局限性

**优点**：
- ✅ 小步快跑，易于调试
- ✅ 可以识别问题补丁

**缺点**：
- ⚠️ 冲突仍然存在
- ⚠️ 时间成本高
- ⚠️ 不解决根本问题

### 2. Vendor代码的特殊性

**关键认知**：
```
小米内核 ≠ upstream内核
小米内核 = upstream基线 + Qualcomm补丁 + 小米定制

直接应用upstream补丁会破坏vendor代码
```

### 3. 正确的更新策略

**错误策略**（我最初采用的）：
```
❌ 直接应用所有upstream补丁
❌ 遇到冲突就跳过
❌ 期望最终能用
```

**正确策略**：
```
✅ 保持小米原版
✅ 只应用关键安全补丁
✅ 手动移植需要的功能
✅ 充分测试每个改动
```

```bash

# 识别关键改动
git log --oneline v5.4.150..v5.4.302 | grep "security\|fix\|bug"
```

```bash
# 只应用安全补丁
git cherry-pick <security-patch-commit>

# 只应用关键bug修复

# 跳过功能改动、重构等
```

